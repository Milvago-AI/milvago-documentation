# Agent configuration (Windows / Linux)

The agent is configured by a **TOML** file, `milvago.toml`, written by the installer and edited by the administrator. It is **applied within a few seconds, without restarting the service**: the file is re-read at most once every 5 seconds.

![Milvago - Agent configuration (Windows / Linux)](/img/docs/fr/avance-agent-configuration-01.png)

## Change the configuration

1. Open the path for your edition and operating system in the table below with an administrator account.
2. Edit the `milvago.toml` file at that path, without changing its access permissions.
3. Save the file; do not restart the service.
4. Wait no more than five seconds, then check `agent.log` in the adjacent `logs` directory to confirm the configuration was applied or read the error.

## Where the file lives

On Windows, the file lives in the `config` directory, **beside the encrypted store, never inside it**. On Linux, it now lives directly under `/etc`, away from the encrypted store and the logs, which stay under `/var/lib`:

| | Windows | Linux (packaged installation) |
| --- | --- | --- |
| Community | `%ProgramData%\Milvago\Browser\config\milvago.toml` | `/etc/milvago-browser/milvago.toml` |
| Enterprise | `%ProgramData%\Milvago\Commercial\config\milvago.toml` | `/etc/milvago-commercial/milvago.toml` |

The access rules are part of the mechanism. On Windows, the `config` directory belongs to **Administrators and SYSTEM**, and the service account only gets **read** — its ProgramData folders now name the service's own SID (`NT SERVICE\Milvago Agent Logger Community` / `NT SERVICE\Milvago Agent Logger`) rather than the NetworkService account as a whole, shared with other services. On Linux, the file belongs to **root** (mode `0640`, group `milvago-agent` in read). The agent can write its own encrypted state; it must not be able to choose the certificate authorities it trusts, or open its listener to the network. This file carries that boundary.

Reinstalling with `install-browser.sh`, or upgrading the RPM package, moves an existing file once from the former location (`/var/lib/milvago-browser/config/milvago.toml` or `/var/lib/milvago-commercial/config/milvago.toml`) to the new one — only if it is a regular file, never through a symbolic link. Once that move has happened, the former location is no longer read.

## The file as the installer creates it

```toml
# Milvago agent configuration. Edited by administrators; the service can only read it.
# Applies within a few seconds, no restart needed.

[queue]
# Main offline event queue only, not total agent memory or disk usage.
# max_events: 1..100000; max_size_mb: 1..128 MiB.
max_events = 10000
max_size_mb = 8

[logging]
# off | error | warn | info | debug. The log is agent.log in the logs directory
# beside this one. It never contains prompt text, response text, file names,
# tokens, credentials or policy content.
level = "info"
# max_file_mb: 1..100 MiB; retained_files: 0..20 archives plus the current file.
max_file_mb = 10
retained_files = 5

[tls]
# HTTPS verification is always on. This only adds one certificate authority to
# the agent's own HTTP client: the server name and the certificate validity are
# still checked, and neither the Windows certificate store nor the browser is
# affected. A declared authority that cannot be read is an error that blocks the
# call; it never falls back to an unverified connection.
allow_private_ca = false
ca_file = ""
# Also trust the root store of the operating system (for instance a TLS-inspection
# authority your organization deploys by policy). Off unless you decide it.
system_store = false

[network]
# One explicit HTTP(S) proxy, "http://host:port", without credentials. Empty means
# direct connections; environment proxy variables are never used.
proxy = ""
bind_address = "127.0.0.1"
allowed_peers = []
```

The file generated by the installer comes from the agent itself: what the operator finds on disk and what the agent applies are the same thing, not two texts maintained by hand.

## `[queue]` — offline event queue

| Parameter | Default | Bound | What it does |
| --- | --- | --- | --- |
| `max_events` | `10000` | 1 to 100000 | maximum number of events in the main offline queue |
| `max_size_mb` | `8` | 1 to 128 MiB | maximum serialised size of that queue |

This main queue combines legacy and Shadow AI events. It does not limit total agent memory or disk use, and is separate from the browser SYSTEM fallback cache, which has its own limits of 1,000 events or health batches and 8 MiB.

When either limit is reached, the agent refuses the new event and does not acknowledge it. Reducing a limit does not delete existing queued events: delivery continues until the queue returns below the new limit.

To raise the queue to 20,000 events and 16 MiB, and retain logs of 20 MiB with 10 archives, merge these values into the existing sections; do not duplicate either `[queue]` or `[logging]`:

```toml
[queue]
max_events = 20000
max_size_mb = 16

[logging]
# Keep your existing level if it differs.
level = "info"
max_file_mb = 20
retained_files = 10
```

An updated installation retains its existing file. After updating, manually add the `[queue]` section to the `milvago.toml` file if it is absent; an absent `[queue]` section or one of its fields uses its default. Changes take effect without a restart when the file is re-read, at most every 5 seconds.

## `[logging]` — verbosity and retention

| Parameter | Default | Bound | What it does |
| --- | --- | --- | --- |
| `level` | `"info"` | `off`, `error`, `warn`, `info`, `debug` | verbosity of the `agent.log` journal in the neighboring `logs` directory. The journal **never contains** prompt text, response text, file names, tokens, credentials or policy content |
| `max_file_mb` | `10` | 1 to 100 MiB | maximum size of a journal file before rotation |
| `retained_files` | `5` | 0 to 20 archives | number of archives retained, in addition to the current `agent.log` file |

Impossible values (unknown level, size out of bounds, retention > 20) are neither corrected nor ignored: the whole file falls back to the documented defaults, with the reason written in the journal.

## `[tls]` — private certificate authority

| Parameter | Default | What it does |
| --- | --- | --- |
| `allow_private_ca` | `false` | adds **one** private certificate authority to the agent's HTTP client, for a Milvago server served behind an internal PKI |
| `ca_file` | `""` | path of the PEM file **relative to the directory that holds `milvago.toml`** (for example `"certs/ca.pem"`), required if `allow_private_ca = true` |
| `system_store` | `false` | also trusts the authorities in the operating system's root certificate store, in addition to the public roots |

**`allow_private_ca` never disables verification.** The server name and the certificate validity remain checked, the Windows certificate store is not touched, neither is the browser trust. A declared but unreadable authority is an **error that blocks the call** — never a silent fallback to an unverified connection. A file present on disk but not requested (`allow_private_ca = false`) is ignored.

`system_store` widens trust a different way: once on, the agent also trusts every authority the machine's administrators installed in the system store — for instance a TLS-inspection authority deployed by group policy — in addition to the public roots. It stays **off by default**: widening trust to whatever a machine administrator installed is only theirs to decide. Verification itself is never disabled, whatever this setting is.

## `[network]` — outbound proxy and local listening

| Parameter | Default | What it does |
| --- | --- | --- |
| `proxy` | `""` | one explicit HTTP(S) proxy address, written `http://host:port` (or `https://`), without credentials, path or query |
| `bind_address` | `"127.0.0.1"` | the interface where the agent's own listeners accept connections: the local extension server (which serves the signed browser extension packages to browsers on this machine) and, on Enterprise, the native telemetry (OTLP) receiver of the collector |
| `allowed_peers` | `[]` | CIDR ranges (IPv4 or IPv6, at most 50) of the remote peers accepted when `bind_address = "0.0.0.0"` |

Empty, the agent connects directly: proxy environment variables (`HTTPS_PROXY` and the rest) are **never** used — the Windows service account does not receive them anyway. An invalid `proxy` value (a scheme other than `http`/`https`, credentials in the URL, a missing host, a path or query after the port) **blocks network calls** rather than falling back to a direct connection; the reason is written to `agent.log`. Like the rest of the file, this setting applies within a few seconds, without a restart.

Only two values of `bind_address` are accepted: `127.0.0.1` (this machine only, recommended) or `0.0.0.0` (all interfaces). Any other value, or an invalid `allowed_peers` list, keeps the listeners local and the reason is written to `agent.log`. Changing `bind_address` requires restarting the agent service.

Loopback is always accepted; with an empty `allowed_peers` list, no remote peer is accepted even once `0.0.0.0` is opened, and `"0.0.0.0/0"` accepts any IPv4 machine that can reach this one.

:::warning

Opening the listeners exposes these ports to the network: a firewall rule must be opened by the administrator (Windows Defender Firewall / nftables), and it is rarely needed — for example for containers or WSL on the same machine, with `["172.16.0.0/12"]`.

:::

Important limit: the OTLP receiver attributes every telemetry batch to the operating system account that owns the local connection; a remote sender has no local process, so it is still refused even when its address is allowed. Opening the listeners therefore only changes who can reach the extension server.

The model filter (Enterprise) never follows this setting: its confinement requires it to stay local.

## What the file refuses, and why

Each validation rule closes a hijacking path:

- **Relative path only**: an absolute path, a `..`, a symbolic link or a junction would let whoever writes the value make the agent read a file it is not supposed to read. The file is also **regular** (not a link), limited to 256 KiB (an authority is a few PEM blocks), and the resolved path must stay **within the directory that holds `milvago.toml`** — a junction placed higher in the tree is refused.
- **Unknown fields refused** (`deny_unknown_fields`): a typo in a parameter name does not become an ignored value.
- **Read-only, never written**: a missing or damaged file resolves to the documented defaults, never to a write attempt the service account has no right to make. A broken configuration can therefore **lower the verbosity, never loosen TLS**.
- **The TLS of an old install is not reinterpreted**: the verbosity of a previous installation (`state\milvago.conf`, `log_level` key) survives the update, but that file never carried a TLS section and can never become a trust setting.

## Self-update under a deployment tool (Windows)

When a deployment tool (Intune, SCCM/ConfigMgr, GPO software installation) already owns the agent's versions, the agent's own self-update turns itself off so it does not fight that tool — otherwise the tool would reinstall the old package after every automatic update. Either one of the two registry values below turns it off; both sit under `HKLM`, writable by administrators only:

| Location | Value | Origin |
| --- | --- | --- |
| `HKLM\SOFTWARE\Policies\Milvago` | `DisableSelfUpdate` (DWORD) = `1` | GPO / Intune policy |
| `HKLM\SOFTWARE\Milvago\community` (Community) or `HKLM\SOFTWARE\Milvago\commercial` (Enterprise) | `SelfUpdate` (DWORD) = `0` | installer |

The privileged update applier also refuses to act while either value is set. The agent records one line in `agent.log` when self-update turns itself off.

That applier is the Windows service **Milvago Update Applier** (**Milvago Update Applier Community** in Community). It starts with the device and stays running at all times, even with no update in progress: this reserves, from startup, the local channels through which the agent and the browser reach it. Do not disable it; it does nothing until the agent asks it to apply a signed release.

The deployment tool then owns versions: detect the product by its **UpgradeCode** or by the `installation.json` file, never by the **ProductCode**, which changes with every new release.

## Self-update (Linux, archive installation)

For an installation made with the archive and `install-browser.sh` — not the RPM — the agent's self-update is applied by a **root update applier** (`<service>-updater.service`), started by `<service>-updater.path` as soon as the agent files an update request. That applier trusts only `/etc/<name>/release.json` — written by the installer from the provisioning file (update public key and server origin). The agent itself stays unprivileged: it can neither replace its own binary nor change that anchor.

An installation made with a version of `install-browser.sh` older than this change does not update itself: reinstall once with the new script to create these systemd units. Installations made from the **RPM** package keep being updated by the package manager, unchanged.

## Browser policy drift (Windows)

Every 60 seconds, the agent checks that machine policies still force-install its extension:

| Family | Registry |
| --- | --- |
| Chromium (Chrome, Edge, Brave, Chromium, Vivaldi, Arc) | `HKLM\SOFTWARE\Policies\<vendor>\ExtensionInstallForcelist` |
| Firefox | `HKLM\SOFTWARE\Policies\Mozilla\Firefox`, value `ExtensionSettings` |

If an organization Group Policy that owns these lists replaces them, the entries written at installation disappear and browsers uninstall the extension. The agent records one error naming the affected browsers each time this set changes, never on every check; it never rewrites the policy itself.

**Fix**: add the Milvago entries to the organization's own Group Policy that manages these lists. The extension ID and update URL the installer wrote can be read from these same registry keys on an installed machine.

## Cloned images (VDI, sysprep, virtual machine clone) — Windows and Linux

The agent binds its identity to the machine: on Windows, the `MachineGuid` and the machine account SID; on Linux, `/etc/machine-id`.

When a copy of an already installed disk starts on another machine, that copy archives the identity it carried and registers again as a new device, under its own machine name, using the organization's deployment key kept in its encrypted state (subject to the usual enrollment approval rule). The original machine keeps its identity.

If no usable deployment key is available — for instance a device enrolled before this version and never repaired with the organization package, or a key that has since changed (rotation) — the copy **drops its identity** and stays unregistered until the organization package is reinstalled on it: two machines never share one identity.

Which cloning tools actually change these identifiers is still being measured; the supported path is to seal the image as the platform documents: `sysprep /generalize` on Windows, emptying `/etc/machine-id` on Linux.

## In summary

| | Windows | Linux |
| --- | --- | --- |
| Service | display name `Milvago Agent Logger Community` / `Milvago Agent Logger Enterprise`; service name unchanged, `Milvago Agent Logger Community` / `Milvago Agent Logger`, NetworkService account, service's own SID on the ProgramData folders | `systemd` system, `milvago-agent` user |
| Encrypted state | `config` and `logs` are **siblings** of the `state` directory | `logs` stays a **child** of the state directory (`/var/lib`); `config` is now separate, under `/etc` |
| File | `config\milvago.toml`, Administrators + SYSTEM in write, service in read | `milvago.toml`, root in write, `milvago-agent` group in read (mode `0640`) |

A one-off command-line `sync` honors `[tls]` exactly like the service: the same configuration applies to every path that talks to the server.
